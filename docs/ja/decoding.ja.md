# 読み込みの規則

`Decode` と `DecodeFile` が、TOML の文書を Go の値にどう当てはめるかを定めます。
日時を Go のどの型に入れるかは、RFP（`toml-rfp.ja.md`）でこの文書に任されていました。
それ以外の項目は、コードの振る舞いとその理由を記録したものです。

## 値の行き先

| TOML | Go の受け皿 | 補足 |
|---|---|---|
| 文字列 | string 系 | |
| 文字列 | `time.Duration` | `time.ParseDuration` で読む（例: `"1m30s"`）。 |
| 文字列 | `time.Time` | RFC 3339 の書式のとき。日時と同じく、オフセットを名前なしで保つ。 |
| 整数 | int 系・uint 系 | 範囲外は `DecodeError`。負の値を uint に入れる場合もエラー。`time.Duration` に入れるとナノ秒として扱う。 |
| 整数 | float32 / float64 | 正確に表せる場合だけ。例えば `2^53 + 1` を float64 に入れるとエラー。 |
| 浮動小数点数 | float32 / float64 | float32 に収まらなければエラー。`inf` と `nan` は通る。整数の受け皿には入れない。 |
| 真偽値 | bool 系 | |
| オフセットつき日時 | `time.Time` | 書かれたオフセットを名前なしで保つ。オフセット 0 は `time.UTC` にする。 |
| ローカル日時 | `toml.LocalDateTime` | `time.Time` には入れない（理由は下記）。 |
| ローカル日付 | `toml.LocalDate` | |
| ローカル時刻 | `toml.LocalTime` | `Second` は 60 になりうる。 |
| 配列 | スライス | 丸ごと置き換える。 |
| 配列 | Go の配列 | 長さまで入れ、残りはゼロにする。長さを超えるとエラー。 |
| 表 | 構造体 | フィールドとの対応は下記。 |
| 表 | `map[string]T` | キーは string 系の型ならよい。既にある項目は残し、文書が書いた項目は既にある値の上に重ねる。 |
| 何でも | `any` | `map[string]any`、`[]any`、`string`、`int64`、`float64`、`bool`、`time.Time`、`LocalDateTime`、`LocalDate`、`LocalTime` のいずれかになる。 |

ポインタが `toml.Unmarshaler`（`UnmarshalTOML(any) error`）を実装している受け皿には、`any` に入れたときと同じ形の値を渡します。
配列テーブルは、`map[string]any` を要素とする `[]any` として渡ります。
値の形が一つに決まらないキーのためのものです。task-clock の `command` が、argv の配列とシェル用の文字列のどちらも取るのが、この仕組みを入れた理由です。
この受け皿の下にあるキーは、すべて読み込み済みとして扱います。

ポインタが `encoding.TextUnmarshaler` を実装している受け皿には、文字列ならその中身を、日時なら TOML の書式で書いた文字列を渡します。
それ以外の値は `DecodeError` にします。

## 日時

ローカルの 3 種類にはオフセットがないので、ある瞬間を指していません。
`time.Time` に入れるには、文書が何も言っていないのに UTC か `time.Local` のどちらかを選ぶことになります。
選び方を誤ると、値はエラーもなく何時間もずれます。そのため、ローカルの 3 種類はそれぞれ専用の型に入れます。
`time.Time` に入れようとするとエラーになり、メッセージで正しい型を示します。
呼び出し側がタイムゾーンを決めたら、`LocalDateTime.In(loc)` でローカル日時を瞬間に変換できます。

この方針を決めた時点（2026-11-03）で、組織内に日時を読み込んでいるツールは一つもありませんでした。
したがって、ほかの選び方を前提にしているコードはありません。

オフセットは名前のない固定のタイムゾーンとして保ち、`time.Local` の名前は付けません。文書に書かれているのは `+09:00` であって、`JST` ではないからです。
文字列から `time.Time` に読んだ場合も同じです。`time.Parse` だけを使うと、ここでタイムゾーンに名前が付いてしまいます。

うるう秒（秒 60）は、`LocalTime` では 60 のまま保ちます。
`time.Time` に入れたときと `In` を通したときは、`time.Date` の正規化に従って次の分の 0 秒になります。

## 既定値

`Decode` に渡した値は置き換えずに、その上に読み込みます。
文書に書かれていないキーは、元の値のまま残ります。これは、設定済みのポインタの先、入れ子の構造体、map の項目でも同じです。
nil のポインタは、文書がそこに書いたときだけ新しい値を作ります。そのため、ポインタのフィールドで「書かれた」と「書かれていない」を区別できます。
（作った値への読み込みが失敗した場合も、ポインタは設定されたまま残り、エラーを返します。）
ただしスライスと Go の配列だけは例外で、文書の配列で丸ごと置き換えます。

## 構造体のフィールド

ツールをこのライブラリに移しても設定ファイルの意味が変わらないように、`BurntSushi/toml` と同じ規則にしています。

1. タグ `toml:"name"` がフィールドの名前になる。`toml:"-"` はどのキーも受けない。カンマの後のオプション（`,omitempty`）は無視する。
2. タグのない公開フィールドは、Go のフィールド名を名前にする。非公開のフィールドはどのキーも受けない。
3. 名前が完全に一致するキーがなければ、大文字小文字を区別せずに照合する。該当するフィールドが複数あれば、宣言順で最初のものを使う。
4. タグのない埋め込み構造体（または構造体へのポインタ）のフィールドは、外側の構造体のフィールドとして扱う。
   - 同じ名前のフィールドが複数あれば、最も浅いものを使う。
   - 深さが同じなら、タグのあるものを使う。
   - それでも決まらない名前はあいまいとして、どのキーも受けない。
   - nil の埋め込みポインタは、そのフィールドのどれかに書かれたときに作る。

TOML のキーは大文字小文字を区別するので、`name` と `NAME` は別のキーです。
同じ表の 2 つのキーが規則 3 によって同じフィールドに行き着く場合は、`DecodeError` にします。
そうしないと、2 つの値のどちらかが何の知らせもなく消えるからです。

## 知らないキー

構造体に対応するフィールドがないキーは、読み込まずに集めておきます。
構造体に対応するフィールドがない表は、その下のキーもすべて合わせて集めます。
そのため、`[workspace]` を削除したツールでも、`workspace.workspace_dir` という名前で見つけられます。
ほかのエラーなしに読み込みが終わったら、集めたキーをすべて、文書に書かれた順に `UnknownKeysError` で返します。
配列テーブルの中のキーは、添字なしの名前で 1 回だけ挙げます。
この時点で、知っているキーはすべて読み込み済みです。`AllowUnknownKeys()` を渡すと、知らないキーは読み飛ばします。

map、`any`、`Unmarshaler` の受け皿はどのキーも受けます。ただし、map の中の構造体は別です。
例えば `[servers.main] colour = "red"` を `map[string]Server` に読み込むと、`Server` に該当するフィールドがなければ `servers.main.colour` を挙げます。

## エラー

| エラー | 起きるとき | 持っている情報 |
|---|---|---|
| `*ParseError` | 文書が TOML 1.1.0 ではない | Line、Column（文字数）、Msg |
| `*DecodeError` | 値が受け皿に合わない | Key、Line、Msg。`UnmarshalText`、`UnmarshalTOML`、`time.Parse`、`time.ParseDuration` のエラーを取り出せる |
| `*UnknownKeysError` | 受け皿のないキーがある | 文書に書かれた順の Keys |

読み込みは最初の `DecodeError` で止まるので、値には文書の一部だけが入っていることがあります。
メッセージでは、キーをルートからの名前で示します。メッセージは、文書の中身にかかわらず小さく保ちます。

- キーのパートやトークンは、40 文字まで引用します。
- 受け皿のメソッドが返したエラーは、200 文字まで引用します。エラー全体は `errors.Unwrap` で取り出せます。
- `UnknownKeysError` が名前を挙げるキーは、10 個までです。

自分自身を指すポインタ型（`type P *P`）は、無限ループにせず `DecodeError` にします。

## BurntSushi/toml との違い

どの違いについても、2026-11-03 に組織内のツールを調べています。
移行するツールの作業が変わるのは最初の 2 つだけで、残りはどのツールも使っていない範囲の違いです。

- **知らないキーは既定でエラーにします。** BurntSushi は `Undecoded()` で一覧にするだけで、読み込みは続けます。
  `Undecoded()` はありません。その一覧から独自のメッセージを組み立てていたツールは、`errors.As` で `UnknownKeysError.Keys` を読むように書き換えます。
  読み込みを続けたいときは `AllowUnknownKeys()` を渡します。
- **メッセージの文面はこのライブラリ独自のものです。** BurntSushi の文面と比べているテストは、移行のときに直します。
- **大文字小文字だけが違う 2 つのキーが同じフィールドに行き着くと、エラーにします。** BurntSushi は後に書かれたほうを採ります。
- **ローカル日時は `time.Time` に入れません。** BurntSushi は仮のタイムゾーンを付けて入れます（「日時」の節を参照）。
- **`TextUnmarshaler` に渡すのは文字列と日時だけです。** BurntSushi は整数・浮動小数点数・真偽値も文字列にして渡します。
  組織内の `TextUnmarshaler` は期間（duration）の型だけで、どちらのライブラリでも数字だけの値は拒否します。
- **スライスは丸ごと置き換えます。** BurntSushi は既にある要素の中に読み込むので、要素の中の既定値が残ります。
- **map の項目は、文書が書いた分を既にある値の上に重ねます。** BurntSushi は項目ごとに新しく作ります。
- **Go の配列には長さまで入れます。** BurntSushi は長さがぴったり一致することを求めます。
- **整数を浮動小数点数に入れるのは、正確に表せる場合だけです。** BurntSushi は ±2^53 までを受け付け、それを超えると拒否します。
  このライブラリでは 2^60 は通り、2^53 + 1 は通りません。
- **`map[any]T` は受け皿にできません。** map のキーは string 系の型に限ります。
- **`Unmarshaler` には、配列テーブルを `[]any` で渡します**（BurntSushi は `[]map[string]any`）。ローカル日時はローカルの型で渡します（BurntSushi は `time.Time`）。
- **`DecodeFile` は 1 MiB までしか読みません。**
- **`Primitive`、`PrimitiveDecode`、`Keys()`、`Type()`、`NewDecoder`、`DecodeFS`、書き出し機能はありません。** 使っているツールはありません。

## 上限

- 文書は 1 MiB まで（`DecodeFile` もそれ以上は読みません）。
- 表と配列の入れ子は 128 段まで。
- キーは 128 パートまで。

入力の上限は、そのままメモリの上限でもあります。最悪の場合、構文解析した木は文書の大きさの約 85 倍になります。
